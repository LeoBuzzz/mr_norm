# Архив спецификации этапа 1 v1: LLM-разбор вопроса в dry-run план скиллов

Версия: 1.0. Дата: 2026-10-06.
План: [PLAN_QUESTION_PARSER.md](PLAN_QUESTION_PARSER.md).
Исполнитель: Luna 6, среднее усилие. Документ задаёт реализацию и приёмку;
код и live-измерения этой задачей ещё не выполнены.

## 1. Измеримый результат и границы

Одна новая функция в существующей песочнице принимает вопрос и структурированный
контекст, выполняет классификацию лёгкой LLM, затем отдельный разбор лёгкой или
тяжёлой LLM, проверяет результат и возвращает сериализуемый план.

Этап не вызывает поиск, Qdrant, reranker, скиллы или генерацию ответа.
Исполнение зависимых цепочек, постоянное хранение диалога и подключение бота
отложены. Однако зависимость и неподдержанное намерение должны быть распознаны:
запрещено потерять их и выдать неполный план со статусом `ready`.

Поддержать независимые вызовы `exact_point`, `corpus_point_search`, `find_all`.
Несколько вызовов одного скилла допустимы. Не добавлять новые поисковые скиллы.

## 3. Публичный интерфейс

Ориентир сигнатуры; допускается явный dataclass вместо именованного словаря:

```python
plan_skill_query(
    query: str,
    *,
    dialog_context=None,
    pending_clarification=None,
    catalog,
    knowledge,
    llm_adapter,
    config,
) -> SkillQueryPlan
```

`catalog` и `knowledge` передаются извне; не загружать полный корпус чанков.
Контекст можно получить адаптером существующего `DialogContext`. Адаптер не
мутирует переданный объект. В тестах достаточно структурированных снимков.

`llm_adapter` принимает роль (`classifier`, `simple_parser`, `complex_parser`),
messages, model, timeout и max_tokens; возвращает content, фактическую model,
usage при наличии. Использовать существующий LLM-клиент для реального вызова.
В тестах передавать управляемый адаптер без сети. Все роли и модели отражаются
в trace; автоматическая незаметная смена провайдера/модели запрещена.

Конфигурация: явные `light_model`, `heavy_model`, provider; `max_tasks=6`,
`max_query_chars=8000`, `max_context_chars=16000`, timeout 60 с на вызов;
лимиты выхода classifier 256 токенов, parser 4096. Это начальные ограничения
пилота, не заявленные характеристики выбранных моделей.
Переполнение входа возвращает `input_limit_exceeded`, без молчаливого обрезания
условий. Предельный контекст считается после сериализации перед вызовом.

## 4. Подготовка контекста и словаря

Передавать точный `original_query`, не заменяя его нормализованным текстом.
Разделять пользовательский текст, контекст и инструкции system prompt.
Текст вопроса/документа не может переопределять перечень скиллов или схему.

Контекст включает ID ходов, их пользовательские тексты, подтверждённые doc_id,
номера пунктов и условия. Не передавать длинные найденные нормативные тексты.
Подтверждённое условие должно иметь ссылку на ход и исходную формулировку;
неподтверждённую догадку предыдущей модели не повышать до подтверждённого факта.

Использовать `match_query_terms` и общий словарь. Для совпавших сокращений
сохранять все доступные расшифровки группы; если штатный лимит выдачи обрезал
группу, восстановить её из уже загруженного knowledge, не создавать новый
словарь. Не передавать всю базу сокращений в prompt.
Для аббревиатур, совпадающих с обычными словами, соблюдать существующую
фильтрацию. Отдельно сохранять морфологические варианты и варианты сокращений.

Совпадение строки и расшифровки не доказывает равнозначность нескольких
значений. При разных подходящих значениях без разрешающего контекста требуется
уточнение. Каталог даёт кандидатов документов; LLM выбирает только из них.
Код заново проверяет выбранный doc_id. Подтверждённый doc_id контекста также
должен существовать в переданном каталоге.

## 5. Классификатор: первый вызов

Строгий ответ: `{"complexity":"simple|complex","reason_codes":[...]}`.
Допустимые reason_codes: `single_intent`, `multiple_intents`,
`multiple_targets`, `dependency`, `comparison`, `context_correction`,
`ambiguity`, `unsupported_intent`, `uncertain`.
Не принимать лишние поля со скиллами/планом как результат парсинга.

Простой: одна задача и одна область поиска, без зависимости и неразрешённой
неоднозначности. Несколько условий одной задачи сами по себе не делают её
сложной. Однозначное «А пункт 2.1?» в подтверждённом контексте может быть простым.
Сложный: несколько целей/намерений, зависимость, сравнение, коррекция прежнего
условия, неразрешённая неоднозначность или неуверенность классификатора.

Второй вызов обязателен для обоих классов: simple_parser использует light_model,
complex_parser — heavy_model. Классификатор не вызывает инструменты.

## 6. Контракт результата парсера

Использовать dataclasses и явную валидацию либо уже имеющуюся в проекте
библиотеку. Не вводить новую зависимость только ради схемы.

SkillQueryPlan содержит:

- `schema_version`: `skill_query_plan.v1`.
- `original_query`: точная исходная строка; устанавливается кодом.
- `status`: `ready | needs_clarification | deferred | error`.
- `complexity`: результат классификатора; устанавливается кодом.
- `dialog_action`: `new | continue | correct | clarify`.
- `tasks`: упорядоченный список задач, максимум 6, уникальные ID `t1`, `t2`, …
- `clarification`: null или один объект уточнения.
- `issues`: список объектов `code`, `task_ids`, `message`.
- `trace`: технические метрики; устанавливается кодом, не принимается от LLM.

Строгая JSON-схема сырого ответа парсера содержит только `dialog_action`,
`tasks`, `clarification`, `issues`. Остальные поля SkillQueryPlan создаёт код;
status вычисляется после проверки по разделу 7. Для issues парсер может
предлагать только `ambiguous_document`, `ambiguous_term`, `missing_point`,
`ambiguous_scope`, `ambiguous_intent`, `unsupported_intent`,
`dependency_execution_not_in_stage1`. Технические коды добавляет валидатор.
Пустой tasks допустим для error и needs_clarification; ready требует минимум
одну задачу. Issue без clarification не заменяет вопрос при неоднозначности.

Каждая задача содержит:

- `task_id`, `intent_text`, `evidence` — намерение и его текстовое основание.
- `skill`: одно из трёх поддержанных имён или null для неподдержанного действия.
- `query`: отдельный поисковый вопрос задачи, со всеми её условиями.
- `scope`: `corpus | document | unresolved`; `doc_id`: строка либо null;
  `document_mention`: исходное название либо null.
- `point_ref`: строка либо null. Для двух пунктов — две задачи exact_point,
  каждая со своей парой документ–пункт; не независимые списки без связей.
- `coverage`: `exact | ranked | comprehensive`.
- `concepts`: список `{surface, variants, evidence}`. `variants` — только
  подтверждённые словарём/морфологией варианты; догадки хранить в issues.
- `constraints`: список `{id, kind, text, polarity, evidence}`; kind:
  `object | action | condition | quantity | exclusion`; polarity:
  `include | exclude`. Число и единица сохраняются совместно в `text`.
- `depends_on`: список ID предыдущих задач; пустой у независимой задачи.
- `replaces`: список ID условий контекста, явно исправленных этой задачей.

Evidence: `{turn_id, quote}`, где turn_id — `current` или существующий ID хода,
quote — непустая точная подстрока соответствующего пользовательского текста.
Каждое поле `evidence` всегда является непустым списком таких объектов.
Не заставлять LLM вычислять посимвольные координаты.

В снимке контекста каждому подтверждённому условию присвоить стабильный ID.
Проверять, что `replaces` ссылается на существующее условие переданного снимка,
а основание исправления находится в текущем сообщении. При `dialog_action=new`
контекст не может служить единственным основанием документа или ограничения.

Clarification: `{question, target_task_ids, field, options}`. `field` —
`document | term | point | scope | intent`. Options — 0–5 вариантов,
каждый `{id, label}`; использовать только реально имеющиеся кандидаты/значения.
Вопрос должен называть предмет неопределённости, а не «уточните вопрос».
Если неоднозначностей несколько, спрашивать одну с приоритетом document →
term → point → scope → intent; остальные сохранять в issues.

Пример проверки поведения, не готовый ответ модели:
«Покажи пункты 6.25 и 6.26 правил по охране труда» при однозначном каталоге →
complex, две independent задачи exact_point, один подтверждённый doc_id,
point_ref 6.25/6.26, status ready. При двух подходящих документах → уточнение.

## 7. Правила выбора скилла и статуса

- Явная просьба текста конкретного пункта → exact_point, coverage exact,
  обязательны проверенный doc_id и point_ref.
- Поиск пунктов по теме/требованию без требования полноты → corpus_point_search,
  coverage ranked; scope corpus либо конкретный документ.
- Полный перечень/«найди всё» в пределах темы → find_all, coverage comprehensive.
  Слово «все» внутри условия («для всех работников») само по себе не выбирает
  find_all. Comprehensive описывает запрос пользователя, не доказанную полноту.
- `all_mentions` — только старое имя маршрута; в новом контракте использовать
  `find_all`. На этапе 2 адаптер сопоставит его с существующим диспетчером.
- Определение, нормативное заключение, сравнение/саммари как отдельный результат
  не поддержаны этим этапом. Сохранить намерение задачей с skill null,
  status deferred и `unsupported_intent`. Не превращать вывод о применимости
  молча в поиск источников.
- Зависимая задача сохраняет depends_on; весь план получает deferred и
  `dependency_execution_not_in_stage1`. Не выдавать её готовым вызовом.
- Если смысл неясен — needs_clarification. Если ясен, но функция недоступна —
  deferred. Если сломан JSON/контракт/транспорт — error.
- Приоритет итогового статуса: error, затем needs_clarification, затем deferred,
  затем ready. Ready допустим только если все задачи поддержаны и валидны.
- Никакой статус на этапе 1 не запускает скиллы.

## 8. Валидация и ограничение повторов

Проверить типы и enum, уникальность ID, существование doc_id, обязательные поля,
точность evidence, ссылки на контекст, соответствие scope/doc_id, отсутствие
циклов и неизвестных depends_on, запрет самозависимости. Для corpus scope doc_id
должен быть null. Unknown/лишние поля парсера отклонять с диагностикой.

Нормализованные варианты должны иметь основание в переданных словарных данных.
Нельзя принять выдуманный скилл, номер документа или восстановленный «по
похожести» 861 вместо явно указанного 86. Номера пунктов не путать с напряжением,
датой или номером нормативного документа.

Успех: ровно 2 логических LLM-вызова. При schema/contract ошибке второго вызова
разрешён один repair той же модели с перечнем ошибок; всего максимум 3.
Сбой классификатора или transport timeout → error, без эвристического маршрута.
После неуспешного repair → error. Не эскалировать автоматически к тяжёлой модели
на этом этапе: ошибочная классификация должна быть видна в измерениях.
Транспортные повторы существующего клиента учитывать отдельно; для пилота
ограничить их одной попыткой через существующий hook/адаптер, не менять общий
клиент. Не выдавать «2 вызова», скрывая дополнительные физические запросы.

Структурная проверка не доказывает смысловую полноту. Например, удалённое LLM
условие может дать валидный JSON. Такие ошибки выявляет эталонная оценка ниже.

## 9. Память диалога в первом этапе

Поддержать на переданном контексте:

1. «А пункт 2.1?» — наследовать однозначный документ и заменить номер.
2. «Не электростанции, а подстанции» — заменить условие, заполнить replaces,
   не сохранять одновременно оба включённых объекта.
3. «Теперь только по ПУЭ» — изменить область, сохранить тему при явной связи.
4. Новый самостоятельный вопрос — не наследовать прежний документ/напряжение.
5. Ответ на pending_clarification — сохранить исходную задачу и применить
   уточнение; исходная неоднозначная задача и вопрос уточнения передаются
   структурированно. Неподходящий ответ оставляет needs_clarification.
6. «Эти пункты» при отсутствии однозначных ссылок — уточнение.

Результат описывает новое состояние через задачи и replaces; запись в память
не выполняется. Отдельный новый framework памяти не создавать.

## 10. Набор оценки и тесты

Создать 40 фиксированных случаев: 20 tuning + 20 holdout. Распределение:
8 простых одиночных, 6 составных независимых, 6 словарных/морфологических,
8 диалоговых (включая уточнение), 6 неоднозначных, 6 зависимых/неподдержанных.
Каждую группу разделить поровну между tuning и holdout. В обеих половинах
должны быть simple и complex. Обязательные числа, отрицания и ограничения
добавлять как сквозные признаки, не отдельные однословные вопросы.

Использовать подходящие реальные вопросы из существующих fixtures, сохраняя
их исходный split. Дополнения помечать synthetic. Не называть перефразировку
tuning-вопроса независимым holdout. Эталон зафиксировать до live-прогона и
записать хеш; не получать ожидаемый ответ той же моделью в том же прогоне.

Для каждого случая: ID, split, provenance, question, context, фиксированные
кандидаты каталога/словаря, expected complexity/status, tasks с ожидаемыми
skill/doc_id/point_ref/coverage, обязательные constraints и evidence,
допустимые уточнения, зависимости и запрещённые подстановки.
Не требовать дословного совпадения поисковой формулировки или текста уточнения.
Порядок независимых задач не важен; пары документ–пункт и зависимости важны.

Обязательные примеры поведения:

- «Покажи пункты 6.25 и 6.26 правил по охране труда»: обе пары сохранены.
- «Найди требования к заземлению ВЛ 110 кВ, не кабельных линий»: одна тема,
  исходные ВЛ, 110 кВ и исключение сохранены; словарь не стирает условия.
- «Найди все пункты про работу под наведённым напряжением на ЛЭП»: find_all;
  ЛЭП не подменяется более узкой ВЛ без основания из контекста/словаря.
- «Найди требования для всех работников»: слово «всех» не означает full scan.
- «Что такое ВЛ и покажи пункт 1.1.1 ПУЭ»: обе задачи сохранены; первая
  unsupported, вторая exact_point; общий статус deferred.
- «Пункт 33 постановления 86»: не исправлять на 861; уточнение при отсутствии
  однозначного кандидата, даже если каталог содержит популярный документ 861.
- «Найди пункты о заземлении и затем сравни их требования»: зависимость и
  неподдержанное сравнение явно сохранены, status deferred.
- Одинаковая тема с сокращением и полным названием: одинаковые skill/scope и
  совместимые concept variants. Это metamorphic-пара, а не два независимых gold.

Дополнительно контрактные тесты с fake adapter: выбор двух ролей, JSON error,
timeout, 1 repair, предел 3 вызова, неизвестный skill/doc_id, выдуманная цитата,
неизвестный ход, цикл, 7 задач, превышение входа, отсутствие мутации контекста,
нулевые вызовы скиллов/сети. Fake-ответы проверяют оркестрацию, не интеллект LLM.

## 11. Измерения и критерии приёмки

Offline gate:

- Все новые контрактные тесты и существующие test_router.py и
  tests/test_abbreviations.py проходят. После изменений исполнять также
  test_skills.py и test_skill_extensions.py для проверки совместимости.
- 40 эталонов проходят проверку схемы/уникальности/разделения split.
- Fake adapter подтверждает 2 вызова в норме, максимум 3 с repair и отсутствие
  фактического поиска. Никаких новых production side effects.

Live gate (20 holdout, один проход после настройки на tuning):

- Классификация верна минимум на 18/20; все размеченные зависимости,
  составные задачи и неоднозначности направлены к complex_parser.
- Полный ожидаемый план/статус верен минимум на 18/20. Случай считается верным,
  только если совпали задачи, пары документов/пунктов, охват, ограничения и
  требуемое уточнение/deferred. Совпадения одного primary недостаточно.
- Ноль потерянных/перевёрнутых обязательных отрицаний, чисел с единицами,
  неверных doc_id и пропущенных намерений во всех принятых ready-планах.
- Все неоднозначные случаи возвращают конкретное уточнение без угадывания;
  не более одного ненужного уточнения на однозначных случаях holdout.
- Ноль ready-планов с неподдержанной операцией или зависимой цепочкой.
- Технические ошибки считаются неуспехом, не удаляются из знаменателя.

Сохранить по случаю: raw classifier/parser replies, итоговый план, validation
errors, actual model/provider, prompt version/hash, elapsed каждого вызова,
usage или null, число логических и физических вызовов, repair count,
expected/actual comparison. Без ключей, токенов авторизации и полных секретных
настроек. Отчёт: отдельные tuning/holdout метрики и p50/p95 задержки по классам.
Если денежная цена не измерена по проверенному тарифу — null, не оценка на глаз.
Порог скорости на первом пилоте не задавать: собрать baseline.

Конкретные runtime-модели и провайдер пока не выбраны. Реализовать и завершить
offline gate независимо; live gate запускать с явно заданной конфигурацией.
Отсутствие провайдера обозначать `live_not_run`, не «этап полностью принят».
20 holdout случаев дают пилотную оценку, не доказательство качества на всех
возможных вопросах. При провале не перенастраиваться на holdout молча:
зафиксировать ошибки и версию, следующий контроль проводить на новом наборе.

## 12. Порядок работы для Luna 6 medium

1. Сверить сигнатуры, выписать использованные компоненты и создать схемы/типы.
2. Создать 40 эталонов и валидатор набора; заморозить split и ожидаемые поля.
3. Добавить подготовку контекста/словаря и тесты на сокращения и перенос условий.
4. Добавить два промпта (classifier и общий parser), выбор роли и fake adapter.
5. Реализовать валидацию, repair, статусы и dry-run API в текущем роутере.
6. Выполнить offline gate; исправить дефекты без изменения старого поведения.
7. Добавить eval CLI: --split, --light-model, --heavy-model, --provider,
   --output. Fake-режим явно помечать, live-режим включать явно.
8. При наличии runtime-конфигурации выполнить tuning, затем один holdout.
9. Сохранить `REPORT_QUESTION_PARSER_STAGE1.md` и JSON отчёт с фактическими
   результатами, незавершёнными пунктами и воспроизводимыми командами.

Не расширять этап до реализации executor, цепочек, собственного словаря,
новых поисковых алгоритмов или отдельного хранилища памяти. Если требуемое
переиспользование невозможно без production-изменений, описать конкретный
разрыв и сделать локальный адаптер в пределах указанного контракта.
