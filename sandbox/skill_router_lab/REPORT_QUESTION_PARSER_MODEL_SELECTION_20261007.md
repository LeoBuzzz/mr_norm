# Выбор runtime-моделей парсера вопросов через Polza

Дата: 2026-10-07. Провайдер: `polza`. Ключ загружен существующим кодом проекта;
значение ключа не выводилось и не сохранялось в отчётах.

## Решение

Выбранная пара для следующей итерации после исправления модельного контракта:

- classifier: `openai/gpt-6-sol`;
- simple_parser: `openai/gpt-6-sol`;
- complex_parser: `openai/gpt-6-astra`.

Текущий `RouterPlanConfig` использует один `light_model` одновременно для
classifier и simple_parser, поэтому эти две роли пока нельзя настраивать
независимо. Выбранные параметры CLI: `light_model=openai/gpt-6-sol`,
`heavy_model=openai/gpt-6-astra`.

Эта конфигурация **не активирована для holdout**. Ни одна проверенная пара не
прошла tuning gate. Модели выбраны как лучшие кандидаты для следующего цикла,
а не как доказанно готовая production-конфигурация.

## Почему tuning не прошёл

Ошибки повторяются у разных семейств моделей, включая старшие:

- модель возвращает `null` вместо обязательных массивов;
- evidence является пересказом, а не точной подстрокой источника;
- генерируются произвольные issue-коды;
- clarification не соответствует строгой схеме;
- нарушаются допустимые сочетания `skill / scope / coverage`;
- repair-вызов часто повторяет структурную ошибку.

Это показывает ограничение интерфейса: `response_format=json_object` гарантирует
JSON-объект, но не контракт `skill_query_plan.v1`. Сейчас модель должна вручную
воспроизвести большую схему и точные цитаты. Замена на более дорогую модель
улучшает классификацию, но не решает структурную надёжность.

## Следующий обязательный шаг

До повторного tuning и единственного holdout-прогона:

1. Передавать провайдеру JSON Schema через structured outputs, если выбранная
   модель и Polza поддерживают её для `/chat/completions`; иначе разделить
   модельный ответ на более простой semantic draft и детерминированную сборку.
2. Формировать пустые массивы и технические поля кодом, а не просить модель.
3. Evidence привязывать к переданным фрагментам по ID или находить точную цитату
   кодом; модель не должна воспроизводить её посимвольно.
4. Issue-коды и итоговый status вычислять валидатором из разобранных полей.
5. Повторить tuning с выбранными Sol/Astra. Только после прохождения tuning
   зафиксировать конфигурацию и один раз запустить закрытый holdout.

Дешёвую Luna можно повторно рассматривать после упрощения контракта. В текущем
контракте её результат существенно хуже Sol/Astra, поэтому назначать её
classifier/simple_parser сейчас не следует.
