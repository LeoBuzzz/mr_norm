# Песочница разбора вопроса

## Router2: рабочий запуск

Из корня проекта запустите `router2.bat`. В терминале появится приглашение
`router2>`; введите вопрос. `exit` завершает работу, `new` сбрасывает
ожидающее уточнение. Для одного вопроса используйте
`router2.bat --query "Ваш вопрос"`. Параметры `--router-model`,
`--answer-model` и `--collection` переопределяют настройки запуска.

Router2 использует модельный `route_question`, проверяет план и исполняет
названные скиллы через рабочую Qdrant-коллекцию `mr_norm_docs_bge_m3`.
`exact_point`, `corpus_point_search`, `vector_search` и `find_all` читают
основной индекс; `definition_search` читает локальный
`probe/term-definitions.jsonl`. Найденные фрагменты передаются финальной
LLM через модуль ответа `mr_norm`. Финальная инструкция роутера сохраняется
отдельно от поисковых вызовов. Трассы сохраняются в
`tmp/router2_traces/` (отключаются флагом `--no-trace`).

Перед передачей доказательств финальной модели Router2 автоматически
догружает все части каждого найденного нумерованного пункта. Для точного
выбора используется `point_identity_key`, поэтому пункты с одинаковым номером
в разных разделах не объединяются. Если полный пункт собрать нельзя, исходный
фрагмент сохраняется, а в трассу добавляется предупреждение.

Если роутер раскрыл аббревиатуру по каталогу, поисковые скиллы выполняют оба
варианта запроса: с полным наименованием и с исходной аббревиатурой. Результаты
чередуются и объединяются без повторяющихся чанков; `find_all` передаёт в
финальную обработку до 100 уникальных пунктов вместо обычного лимита 16.

По умолчанию обе модели вызываются через Polza: для маршрутизации
`deepseek/deepseek-v3.2`, для ответа `anthropic/claude-sonnet-4.6`.
Нужен `POLZA_AI_API_KEY` либо локальный файл `keys` в формате основного
процесса, запущенный Qdrant и зависимости из `requirements.txt` вместе с
зависимостями основного проекта. Широкий `find_all` сейчас ограничен 100
фрагментами и помечает результат как потенциально неполный. Песочница
не подменяет штатный процесс приложения.

При технической ошибке или неисполняемом плане Router2 переключается на
резервную модель. Цепочка роутера: `deepseek/deepseek-v3.2` →
`google/gemini-3-flash-preview` → `anthropic/claude-haiku-4.5`; цепочка
ответа: `anthropic/claude-sonnet-4.6` → `openai/gpt-5.5` →
`google/gemini-3-flash-preview`. Параметры `--router-fallback-models` и
`--answer-fallback-models` принимают ID через запятую; пустая строка отключает
резерв. Использованные модели и ошибки предыдущих попыток пишутся в трассу.

Живой вопрос идёт через модель, не через списки оборотов. `route_question` отдаёт модели полный список документов корпуса и пары «аббревиатура — полное наименование», найденные в вопросе. Модель выбирает операцию, id документа, раскрытие и, для поиска, строку запроса в базу. Для текста пункта задание — только id и номер пункта. Сложный вопрос получает свою последовательность вызовов скиллов: у каждого шага свой запрос, независимые шаги не ждут друг друга. Сравнение, вывод и пересказ в эту последовательность не входят. Тематический поиск не выбирает один канал: как в `mr_norm`, вместе идут векторный запрос и текстовый по точным словам вопроса. Для сравнения, вывода и пересказа к этой паре добавляется поиск определений: отличие может быть не в определении, и определение есть не у каждого понятия. Поле `final` — задание модели при подготовке финального ответа по уже добытым результатам, и скиллом оно не исполняется. Код только проверяет, что id и расшифровка есть в переданных таблицах.

Промпт собран по правилам H4 из `mr_norm` (`router_prompts_v3_h4.py`): несколько файлов на одно короткое имя и несколько значений одной аббревиатуры не выбираются молча. Если вопрос называет документ, id берётся из короткого имени, а когда его нет — из полного названия и имени файла. Определение вызывает `definition_search` по `probe/term-definitions.jsonl`: у каждого определения есть `doc_id` файла из таблицы документов.

Таблица документов `tables/documents.json` собрана в формате RegistryEntry из `mr_norm` (`normative_documents_registry.json`, schema_version 1): id, тип, кем утвержден, дата, короткое имя, полное имя, файл. id совпадает с `registry_key`, кроме глав ПУЭ: у каждой главы свой id `pue_<глава>`, утверждающий акт общий. Короткие имена взяты из `document_alias_registry.json`. Аббревиатуры — `tables/abbreviations.json`. Прогон Grok 4.7 по 50 вопросам: `model_route_answers.json`.

Цели исполнения совпадают с планом `sandbox/skill_router_lab` в `LeoBuzzz/mr_norm` (ветка `improve-query-planner-60min`): из вопроса и диалога получить проверяемый план вызовов готовых скиллов и исполнить его. При неоднозначности спрашивать, а не выбирать трактовку молча. Ошибку контракта не превращать в вопрос пользователю.

Этапы:

1. Проверяемый разбор без исполнения. `dry_run` по-прежнему не вызывает скиллы.
2. Независимые вызовы и уточнение. Принятый шаг исполняется один раз, результат лежит под id шага. Пока уточнение не закрыто, поиск не стартует. Ответ подставляется в сохранённый план и не стирает остальные условия.
3. Зависимые цепочки и память сессии. Цикл и ссылка на несуществующий результат не исполняются. Число порождённых вызовов за проход ограничено. Полный текст пункта не читается второй раз. Новый вопрос не забирает прежнюю область поиска. Исправление заменяет условие того же вида. Сессии разных пользователей разделены.
4. Широкий поиск получает один план: исходный вопрос сохраняется, аспекты не строятся вторым независимым разложением. Сохранённый план с другим вопросом отклоняется. Внутренний планировщик по умолчанию выключен, потому что сетевой планировщик не используется; сравнение с внедрённым адаптером пишет, какие условия потерялись и как изменились найденные пункты.
5. Оценка разделяет ошибки разбора, диспетчера и поиска и сравнивает выбор скилла с прежним детерминированным приоритетом. Отчёт: `eval_report.json`. Подключение к рабочему пути не сделано и здесь не решается.

На живом маршруте `compare`, `conclude` и `summarize` не становятся скиллом. В `tools` только добыча, а `final` читает модель, которая пишет ответ. План без единого вызова скилла остаётся `deferred`. Разбор через `dry_run` по-прежнему не исполняет эти операции и определение. `define` на живом маршруте вызывает `definition_search`. Несколько написаний одного значения из каталога терминов — одно значение.

Каталог читается из `probe/term-definitions.jsonl`. Исполнение читает локальные тексты пунктов (`LocalCorpus`) для текстового запроса. `vector_search` остаётся в плане; внешнего векторного индекса песочница не вызывает.

```python
from question_parser.run import dry_run
from question_parser.session import handle_turn
from question_parser.memory import SessionStore
from question_parser.corpus import build_demo_corpus
from question_parser.catalog import load_catalog

plan = dry_run("пункт 1.2.18 ПУЭ")
catalog = load_catalog()
turn = handle_turn(SessionStore(), "user", "пункт 2 ГОСТ 19431", corpus=build_demo_corpus(catalog), catalog=catalog)
```

Черновик модели проверяется через `dry_run(..., draft=...)`. Статусы плана: `ready`, `needs_clarification`, `deferred`. Сбой проверки — `technical_error`.
